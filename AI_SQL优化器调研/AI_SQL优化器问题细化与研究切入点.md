# AI SQL 优化器：原始问题与细化场景

本文讨论查询中已经包含 `AI_FILTER`、`AI_JOIN`、`AI_COMPLETE` 等 AI 算子以后，数据库优化器面临的问题，不涉及 Text-to-SQL。

## 1. AI 对传统优化流程的影响

传统查询优化大致包含以下环节：

```text
SQL / 逻辑计划
       ↓
规则优化（Rule-Based Optimization）
       ↓
统计信息与基数估计
       ↓
代价估计
       ↓
计划空间搜索与物理实现选择
       ↓
执行、反馈与必要的重新优化
```

AI SQL 并没有使这些环节消失。真正的变化是：传统优化器在这些环节中依赖的确定性、可统计性、可加成本和语义等价等假设不再总是成立。

本文据此归纳七类原始问题：

| 编号 | 传统优化器环节 | AI SQL 引入的原始问题 |
|---|---|---|
| P1 | 规则改写 | AI 算子缺少可验证的代数性质和规则前置条件，传统改写规则的适用范围以及新增语义规则的正确性难以判定 |
| P2 | 基数估计 | AI 算子的输出是运行时生成且依赖模型的隐藏分布，传统统计系统无法直接获取和复用 |
| P3 | 代价估计 | 模型调用成本受 token、batch、cache、并发和服务状态影响，传统静态可加模型不足 |
| P4 | 优化目标 | 结果质量会随计划变化，但质量缺少统一表示、估计和跨算子传播方法 |
| P5 | 物理实现选择 | AI 算子的模型、级联、索引和候选生成路径可能改变成本与结果，缺少可比较的物理属性与契约 |
| P6 | 计划搜索 | AI 新增的 placement、实现、执行参数和近似改写使候选空间组合膨胀，并削弱传统等价类组织与剪枝方法 |
| P7 | 执行与反馈 | 模型、数据、缓存和服务状态动态变化，编译期选择的静态计划及已物化结果可能失效 |

它们与《AI SQL 优化器调研》1.4 节 C1—C10 的关系如下。C1—C10 是便于横向检查遗漏的挑战清单；P1—P7 则把这些挑战按照优化器职责重新归并为问题树，两者不是两套互斥分类。

| 原始问题 | 主要对应的 1.4 节挑战 |
|---|---|
| P1 Rule-Based 规则基础 | C1 改写规则、C2 精确与近似改写 |
| P2 AI 输出分布 | C5 可复用统计、C8 编译期与运行期信息 |
| P3 AI 代价 | C6 代价模型、C9 模型服务资源 |
| P4 计划质量 | C7 质量估计与约束，也与 C2 相交 |
| P5 物理实现契约 | C3 中的物理实现维度，也与 C6、C7 相交 |
| P6 计划空间与搜索 | C3 计划空间、C4 搜索效率 |
| P7 动态失效与复用 | C5、C8、C10 非确定性与一致性 |

这七类问题不是七个彼此隔离的选题。它们对应优化器的不同职责，并在具体查询中发生连锁作用：P1 决定哪些逻辑变换合法，P2—P4 提供基数、成本和质量属性，P5 为逻辑算子生成可用的物理候选，P6 组织和搜索完整计划，P7 处理实际执行与估计之间的偏差。

## 2. 公共问题场景

后文主要使用三组场景，避免每个问题都停留在抽象描述上。

### 2.1 商品与评论

```sql
products(pid, title, description, price, category) -- 10 万件商品
reviews(rid, pid, text, stars)          -- 100 万条评论，平均每件商品 10 条
```

查询：找出描述中宣称“静音”，但评论中有人抱怨噪音的商品。

```sql
SELECT DISTINCT p.pid, p.title
FROM products p
JOIN reviews r ON p.pid = r.pid
WHERE AI_FILTER('商品描述宣称静音', p.description)
  AND AI_FILTER('评论在抱怨噪音', r.text);
```

这里的 Join 扇出约为 10：一行商品平均匹配十行评论。扇出表示一侧的一行经过 Join 后平均产生多少行输出。AI 谓词放在这个“行数放大器”之前还是之后，可能显著改变关系处理量、逻辑求值次数和模型调用次数。

### 2.2 客户、订单与商品

```sql
customers(cid, notes)                     -- 100 万客户
orders(oid, cid, pid, amount, item_desc)  -- 1000 万订单
products(pid, category)                   -- 10 万商品
```

```sql
SELECT o.oid
FROM orders o
JOIN customers c ON o.cid = c.cid
JOIN products p ON o.pid = p.pid
WHERE o.amount > 1000
  AND AI_FILTER('客户备注暗示其有流失风险', c.notes)
  AND AI_FILTER('订单商品属于高退货风险品类', o.item_desc);
```

这个场景同时包含普通谓词、两个 AI 谓词和多表 Join，适合观察选择率误差怎样传播到谓词顺序、placement 和局部 Join Order。

### 2.3 买家咨询与 FAQ

```sql
questions(qid, text)              -- 5 万条咨询
faq(fid, label, answer)           -- 200 条标准 FAQ
```

```sql
SELECT q.qid, f.fid
FROM questions q
JOIN faq f
  ON AI_FILTER('该咨询可以由这条 FAQ 回答', q.text, f.answer);
```

朴素逐对判断需要处理 `5 万 × 200 = 1000 万` 个候选对。与普通等值 Join 不同，优化器从这段自然语言条件中看不到显式连接键，也不知道哪些咨询—FAQ 对一定不可能匹配。因此，这个场景适合观察：AI_JOIN 的匹配关系对优化器不透明时，候选对为什么难以安全缩减，以及候选缩减会怎样引入结果遗漏。

## 3. 原始问题及其子问题

### 3.1 P1：AI 算子的 Rule-Based 优化缺少可验证的规则基础

#### 问题由来

传统 Rule-Based Optimization 使用关系代数等价律和算子属性改写逻辑计划。规则是否适用，通常可以根据属性引用、数据类型、Join 类型、函数确定性、完整性约束以及聚合函数的代数性质进行检查。

引入 AI 算子后，原有关系规则并非全部失效。不跨越 AI 算子的关系谓词下推、投影裁剪和常量折叠仍可照常使用；一个只读取单表属性、查询内结果稳定的 `AI_FILTER`，也仍可在满足 Join 类型等传统条件时下推。问题出现在规则需要理解、移动、组合或分解 AI 算子时：优化器可能看不到规则成立所需的确定性、输入依赖、组合性、结合律或语义蕴含关系。

| 传统规则 | 传统规则成立的基础 | 引入 AI 算子后的情况 |
|---|---|---|
| Predicate Pushdown | 属性依赖、Join 类型和函数确定性可检查 | 对输入明确且结果稳定的 AI 谓词仍可使用；缺少确定性、上下文依赖或求值语义声明时只能条件使用 |
| Filter 合并 | `σp(σq(R)) ≡ σp∧q(R)` | 把两个 AI 谓词融合进一个 prompt 会形成新的模型任务，不能直接套用布尔等价律 |
| Partial Aggregate | 聚合函数具有明确的局部状态和合并函数 | 自然语言定义的 AI 聚合通常没有可供优化器检查的结合律、交换律和充分中间状态 |
| Predicate Deduction | 等式、约束和逻辑蕴含能够形式化证明 | 从自然语言谓词推导关系必要条件需要语义理解，推导结果难以机械验证 |

#### P1.1：Filter 合并不能直接扩展为语义谓词融合

场景：找出内容完整且表达正面态度的商品评论。

```sql
SELECT rid
FROM reviews
WHERE AI_FILTER('这条评论的内容完整且有效', text)
  AND AI_FILTER('这条评论表达了正面态度', text);
```

计划 A 分别执行两个 AI 谓词：

```text
数据流向：↑

③ AI_FILTER('表达正面态度', text)
                     |
② AI_FILTER('内容完整且有效', text)
                     |
① Scan reviews
```

计划 B 将两个谓词融合为一次调用：

```text
数据流向：↑

② AI_FILTER('内容完整有效，并且表达正面态度', text)
                     |
① Scan reviews
```

对确定性关系谓词，连续过滤与合取条件严格等价：

```text
σp(σq(R)) ≡ σp∧q(R)
```

语义谓词融合则要求下面的组合关系成立：

```text
LLM(x, p) AND LLM(x, q)
?≡
LLM(x, p AND q)
```

左侧是两次独立判断，右侧是一个同时处理两个要求的新任务。联合 prompt 可能改变模型对条件的解释、判定口径和注意力分配，因此合并后的结果不能由传统布尔等价律推出。

[Sema](https://arxiv.org/abs/2603.11622) 实现了 `SemFilter→SemFilter`、`SemFilter→SemProj`、`SemProj→SemFilter` 和 `SemProj→SemProj` 等四种二元融合模式，并通过参考执行路径和运行时样本限制融合造成的结果偏差。其实验中，融合对不同任务的影响并不一致；在包含多个独立 Semantic Filter 的 Q8 上出现了质量下降。

现有结果说明该规则不能被登记为无条件的等价规则，但论文没有给出发生翻转的具体记录。可控 Demo 需要在同一批输入上比较独立执行与融合执行，提取“独立执行通过、融合后拒绝”及其反向样本，并通过重复执行区分稳定的融合效应和模型自身波动。

#### P1.2：AI 聚合缺少 Partial Aggregate 所需的可分解性质

场景：对每个商品的评论生成“主要投诉点”摘要。

```sql
SELECT pid,
       AI_AGG('归纳这些评论中的主要投诉点', text)
FROM reviews
GROUP BY pid;
```

直接聚合计划：

```text
商品的全部原始评论
          |
       AI_AGG
          |
       投诉点
```

分层聚合计划：

```text
                  商品的全部原始评论
             /                |                \
        分区 1             分区 2              分区 N
           |                  |                  |
    AI_AGG_LOCAL       AI_AGG_LOCAL       AI_AGG_LOCAL
             \                |                /
                    AI_AGG_MERGE
                          |
                       投诉点
```

传统优化器只有在聚合函数 `F` 存在明确的中间状态 `State` 和合并函数 `Merge` 时，才能安全生成 Partial Aggregate：

```text
F(D1 ∪ D2 ∪ ... ∪ Dn)
=
Merge(State(D1), State(D2), ..., State(Dn))
```

`SUM`、`COUNT` 和 `MAX` 的局部状态和合并规则是确定的；`AVG` 也可以通过 `(SUM, COUNT)` 等价合并。对于“归纳主要投诉点”这类 AI 聚合，优化器不知道局部摘要是否构成充分中间状态，也不知道合并过程是否满足结合律和交换律。分层执行因而不能直接沿用传统 Partial Aggregate 的等价性证明。

[Cortex AISQL](https://arxiv.org/abs/2511.07663) 使用 Extract、Combine 和 Summarize 组成增量聚合，并在数据能够直接放入上下文窗口时使用 short-circuit；[DocETL](https://arxiv.org/abs/2410.12189) 使用 batched folding 处理 Reduce，并允许用户声明 Reduce 是否具有结合性。这些系统已经提供可执行方案，但尚未形成优化器可以统一检查的 AI 聚合代数。

可控 Demo 应在相同输入上比较直接聚合、不同分区方式、不同 batch size、不同输入顺序和不同合并树，确认结果差异是否稳定存在，再判断算子应声明严格可分解性，还是只提供带质量边界的近似分解规则。

#### P1.3：自然语言谓词的必要条件难以机械推导和验证

场景：找出内容有效的商品评论。

```sql
SELECT rid
FROM reviews
WHERE AI_FILTER('这是一条内容有效的商品评论', text);
```

假设系统从自然语言谓词中推导出普通关系条件：

```sql
text IS NOT NULL AND text != 'nan'
```

增加这个前置过滤后，计划变为：

```sql
SELECT rid
FROM reviews
WHERE text IS NOT NULL
  AND text != 'nan'
  AND AI_FILTER('这是一条内容有效的商品评论', text);
```

设原语义谓词为 `E(x)`，推导出的关系谓词为 `P(x)`。该改写保持原结果的条件是：

```text
E(x) = true  ⇒  P(x) = true
```

即 `P` 必须是 `E` 的必要条件，才能保证：

```text
σE(R) ≡ σE(σP(R))
```

传统优化器可以使用等式、Check Constraint、主外键和非空约束完成形式化推导。`“内容有效” ⇒ text != 'nan'` 则依赖自然语言含义和具体数据约定。若系统错误地从“正面评论”推出 `stars >= 4`，一条文字明显正面但星级误填为 3 的评论就会在调用 AI 谓词前被错误删除。

[Sema](https://arxiv.org/abs/2603.11622) 已实现 Semantic Filter 的全部或部分 Predicate Deduction，并使用辅助 LLM 和反向自检判断推导出的 SQL 条件是否为原语义谓词的必要条件；自检失败时回退到原始 Semantic Filter。该机制降低了直接错误改写的风险，但 LLM 自检仍不是形式化证明，规则的可靠性依赖模型、prompt、列统计和样本值。

该规则需要同时记录推导条件、蕴含方向、验证方式和置信信息。严格必要条件可以作为无损前置过滤；只能由样本支持的条件会引入假阴性，应作为近似规则进入质量约束，不能与传统约束推导使用相同的正确性标记。

#### 与已有工作的边界

[Horrila（早期版本名 PLOP）](https://arxiv.org/abs/2604.09944) 将 Semantic Join 结构化为笛卡尔积上的 Semantic Filter，并搜索语义算子的等价 placement；Sema 已覆盖语义表达式压缩、关系谓词推导和四种二元算子融合；Cortex AISQL、DocETL 和其他系统也实现了面向 Semantic Join、AI Aggregate 和文档 pipeline 的专用改写。

现有工作表明 AI SQL 已经存在多种 rewrite rule。尚未统一的是传统规则在 AI 算子上的适用条件、AI 专用规则的语义保证、自然语言前置条件的验证方式，以及这些信息在优化器规则接口中的表示。

### 3.2 P2：AI 算子的输出分布缺少可直接获取和复用的统计

#### 问题由来

传统基数估计面向存储在关系表中的属性和具有确定语义的表达式。直方图、最常见值、distinct count、完整性约束和扩展统计都建立在这些可观测对象之上。

`AI_FILTER` 的判断结果在查询执行前并不是表中的已有属性，而是由模型根据自然语言 prompt 临时生成的输出。数据库目录中既没有这个输出的边际分布，也没有它与关系属性、Join key 或其他谓词结果的联合分布。模型、prompt 或物理实现发生变化时，统计对象本身也随之改变。

#### P2.1：AI 谓词的输出不是传统统计目录中的可观测属性

商品表有 10 万行，查询要求找出描述中明确宣称静音的商品：

```sql
SELECT pid, title
FROM products
WHERE AI_FILTER(
    '判断下面的商品描述是否明确宣称商品静音',
    description
);
```

该谓词的输出可以理解成一列尚未生成的布尔值：

```text
claims_quiet_by_model BOOLEAN
```

优化器需要估计这列中 `true` 的比例：

```text
s = P(claims_quiet_by_model = true)
```

若 `s = 1%`，AI 谓词输出约 1000 行；若 `s = 80%`，则输出约 8 万行。这个数量会继续影响后续 Join、排序和其他 AI 算子的输入规模。

普通谓词 `price > 1000` 可以利用 `price` 直方图估计；普通谓词 `category = '耳机'` 可以利用最常见值统计估计。对于 AI 谓词，`description` 的长度、词频和 distinct count 不能直接给出模型会把多少行判为“明确宣称静音”。例如：

```text
“采用静音电机”             → 可能判为 true
“夜间运行不会打扰家人”     → 没有“静音”一词，也可能判为 true
“静音效果并不理想”         → 出现“静音”，但可能判为 false
“不提供任何静音功能”       → 出现“静音”，但应判为 false
```

由于这列隐藏输出尚未物化，传统统计系统也无法直接获得它与商品类别、价格、Join key、Join fanout 或其他谓词结果的联合分布。这些相关性及其对 Join 基数的影响是传统优化器已经面对的问题；AI 增加的困难是参与统计的其中一列在执行模型之前并不存在。

#### P2.2：输出分布与模型、prompt 和物理实现绑定

同一个逻辑查询可以使用不同模型或执行实现：

```sql
SELECT rid
FROM reviews
WHERE AI_FILTER(
    '判断下面的评论是否在抱怨噪音',
    text
);
```

假设表中有 1 万条评论，不同实现可能产生不同数量的 `true`：

| 实现 | 输出 true 的行数 | 输出选择率 |
|---|---:|---:|
| 大模型 M1 | 1200 | 12% |
| 小模型 M2 | 2800 | 28% |
| Proxy→Oracle Cascade | 1500 | 15% |

下游算子实际处理的是所选实现输出的 1200、2800 或 1500 行。因此，选择率不能只绑定逻辑表达式：

```text
Selectivity(AI_FILTER)
```

它至少还与以下对象绑定：

```text
Selectivity(
    自然语言谓词，
    prompt 模板，
    模型及版本，
    推理参数，
    proxy/oracle/cascade 配置，
    输入数据分布
)
```

模型升级、prompt 改写或 cascade 阈值变化后，旧统计即使面对同一张表也可能失效。物理实现尚未选定时，优化器又需要基数估计来比较这些实现及其下游计划，由此形成“先选择实现还是先估计基数”的依赖。

#### P2.3：模型输出基数与真实语义比例不是同一个统计量

假设 1000 条评论经过人工标注，其中 100 条确实在抱怨噪音：

```text
真实语义比例 = 100 / 1000 = 10%
```

模型 M1 的输出为：

```text
真阳性 TP = 90
假阳性 FP = 30
假阴性 FN = 10
模型输出 true = TP + FP = 120
模型输出选择率 = 12%
```

模型 M2 的输出为：

```text
真阳性 TP = 70
假阳性 FP = 230
假阴性 FN = 30
模型输出 true = TP + FP = 300
模型输出选择率 = 30%
```

两种估计目标不能混用：

```text
基数估计关心：下游实际会收到 120 行还是 300 行
质量估计关心：这些输出中有多少 TP、FP 和 FN
```

传统确定性谓词通常把满足谓词的真实集合与算子输出集合视为同一个集合。AI 谓词则需要同时表示真实语义比例、模型输出选择率和条件错误分布。模型错误率不仅影响 P4 中的结果质量，也会通过假正例数量直接改变当前计划的节点基数。

#### P2.4：获取和更新基数统计本身需要执行 AI 算子

普通列统计可以通过扫描或抽样已有列值获得。估计 AI 谓词的输出分布，则必须使用指定模型和 prompt 对样本进行真实或代理判断：

```text
抽取 1000 行
      ↓
执行 1000 次逻辑 AI 判断
      ↓
得到输出选择率及置信区间
```

若两个候选计划的预计执行成本只相差 600 次同类 AI 判断，为区分它们先评估 1000 个样本可能得不偿失；若候选计划可能相差几十万次调用，同样的统计成本则可能合理。模型或 prompt 更新后，已有样本标签还可能需要重新计算。

因此，AI 基数估计除估计误差外还具有显式获取成本。优化器需要同时决定是否获取统计、评估哪些 AI 算子、分配多少样本，以及估计精度何时已经足以区分当前候选计划。历史执行结果、物化 AI 派生列和跨查询缓存可以降低统计成本，但必须记录其对应的模型、prompt、推理参数、数据版本和时间范围。

#### 与已有工作的边界

[Larch](https://arxiv.org/abs/2606.07923) 已研究 Semantic Filter 的学习式选择率预测和谓词求值顺序；[Sema](https://arxiv.org/abs/2603.11622) 在运行时对 Semantic Filter 进行小规模执行，收集选择率和谓词结果；Cortex AISQL 也讨论了通过运行时统计改进 AI 算子 placement。因此，AI 谓词选择率并非完全没有估计方法。

现有方法尚未统一处理统计对象与模型、prompt 和物理实现的绑定关系，模型输出基数与真实语义比例的区分，以及统计获取成本与计划收益之间的权衡。

### 3.3 P3：传统代价模型无法表达 AI 算子的实际成本

#### 问题由来

传统优化器主要估计 CPU、I/O、内存和网络开销，并常把计划总代价近似为各节点代价之和。AI 算子的主要开销来自外部或本地模型推理，其成本会随 token 数、输出长度、batch、cache、并发、硬件和服务状态变化。

因此，“AI_FILTER 每行成本为常数”通常只是一个粗略近似；“调用次数最少”也不必然等于最低延迟、最低费用或最低资源消耗。

#### P3.1：AI 算子成本随输入和输出内容变化

场景：对评论做布尔分类和生成摘要都可以写成逐行 AI 函数，但两者的成本结构不同。

```text
布尔分类：输入 500 tokens，输出 true/false
摘要生成：输入 500 tokens，输出约 300 tokens
```

即使使用同一模型，输出 token 的生成速度和价格也可能不同于输入；评论长度又可能从几十到几千 tokens。若优化器只保存“每行一次调用”的固定成本，就无法比较先过滤长文本还是短文本，也无法估计生成算子的总费用和延迟。

需要建立的不是一个统一常数，而是能反映输入长度分布、预期输出长度、任务类型和模型计费方式的成本描述，并判断需要多细的分布信息才足以区分计划。

#### P3.2：batch、缓存和前缀复用使成本不再按行相加

商品描述谓词在 Join 前处理 10 万行，在 Join 后处理 100 万行；但 Join 后仍只有约 10 万个不同商品描述。如果系统按完整的模型、prompt 和输入缓存结果，二者的实际模型计算量可能接近，而缓存查询和关系中间结果成本不同。

另一个查询为每条评论生成带商品标题的翻译：

```sql
AI_COMPLETE('商品标题：' || p.title ||
            '；请翻译评论：' || r.text)
```

同一商品的评论连续输出时，可以形成相同前缀的 batch 或命中 KV-cache；交错输出时复用收益下降。Hash Join 可能在关系侧更快，`Sort + AI_COMPLETE` 却可能因请求组织更好而获得更低的端到端成本。

因此代价模型必须区分输入元组数、distinct input 数、API 请求数和模型实际计算量，并表达 batch 填充率、尾批、缓存命中及输出顺序带来的非加性收益。

#### P3.3：模型服务状态和多种成本目标无法由单一静态代价表示

场景：同一个 AI 谓词有本地小模型和远端大模型两种实现。

```text
本地模型：没有 API 费用，正常延迟低，但 GPU 可能排队
远端模型：按 token 计费，可获得更高并发，但存在限流和重试
```

计划 A 可能费用低但延迟高，计划 B 延迟低但更贵；高峰期 GPU 饱和或 API 限流后，两者顺序又会改变。与此同时，高扇出 Join 即使模型结果大量命中缓存，也可能产生很高的关系执行成本。

需要明确时间、token、货币、GPU 和关系资源是合成为一个成本，还是以约束和 Pareto 维度表示；哪些状态可以在编译期预测，哪些只能在运行时更新；关系成本与推理成本之间的换算能否跨查询规模复用。

#### 与已有工作的边界

Cortex AISQL 将 AI 推理成本作为优化目标；Horrila 在计划级权衡 LLM 调用与关系处理；[FlockMTL](https://arxiv.org/abs/2504.01157) 支持 batching 等执行优化；[Abacus](https://arxiv.org/abs/2505.14661) 比较成本、延迟与质量约束。这里不能笼统声称“没有 AI 代价模型”，需要进一步研究的是不同成本因素的组合是否可预测、哪些推理侧状态必须成为计划属性，以及现有模型在哪些计划决策上产生稳定误差。

### 3.4 P4：结果质量成为计划属性，但缺少可组合的表示

#### 问题由来

传统等价计划通常被认为返回相同结果，优化器只需比较执行成本。AI SQL 中，不同模型、级联阈值、谓词融合和近似候选缩减都可能改变输出。优化器面对的不再只是“哪个计划更快”，还包括“哪个计划的结果仍然满足用户要求”。

质量不是一个天然统一的数字：分类可以用 precision、recall、F1，排序可以用 NDCG，生成结果可能需要任务相关评价；而用户约束通常针对最终查询结果，不是单个 AI 算子。

#### P4.1：不同 AI 算子的质量不能用同一个“准确率”表示

场景：一个查询先过滤负面评论，再对候选评论排序，最后为每个商品生成摘要。

```text
AI_FILTER：关心 precision、recall、F1
AI_RERANK：关心 Top-K recall、NDCG
AI_AGG：关心事实覆盖、忠实度和遗漏
```

即使三个算子各自都有 90 分，也不能据此得到整个查询“90 分”。过滤阶段漏掉的评论不会进入排序和摘要；排序位置错误与摘要事实错误的后果也不同。

需要为不同逻辑算子定义哪些质量属性会影响后续关系操作，并确定优化器是否需要统一质量表示，还是保留一组与算子类型相关的属性。

#### P4.2：局部错误经过关系算子后会产生不同的查询级后果

场景一：FAQ semantic join 先用 embedding 召回 Top-K，再由大模型验证。验证器 precision 很高，也无法恢复召回阶段漏掉的正确 FAQ。若每条咨询可能匹配多个 FAQ，最终 recall 还与真实匹配数分布有关。

场景二：商品查询包含两个 AI 谓词：

```text
Pproduct：商品宣称静音
Preview：评论抱怨噪音
最终条件：Pproduct AND Preview
```

`Pproduct` 的一个假阴性会删除该商品及其所有评论；`Preview` 的一个假阳性则可能使商品错误进入结果。两个谓词在含糊表达上还可能相关出错。简单地把两个算子的 F1 相乘，无法推出最终查询的 precision 和 recall。

需要研究错误如何经过 AND、OR、Join、DISTINCT、GROUP BY 和 Top-K 传播；在什么独立性或数据分布假设下可以组合，以及缺少这些假设时能给出什么上下界。

#### P4.3：质量约束缺少可靠参照和计划级表达

假设用户要求“FAQ 匹配 recall 不低于 95%”。优化器需要在逐对判断、分类和 Top-K 检索计划中排除不合格方案。但 1000 万候选对无法全部人工标注，大模型 oracle 也可能与人工判断不一致；同一计划重复执行时，边界样本还可能变化。

因此至少有三个待确定的问题：质量以人工标签、强模型还是原始计划为参照；一次校准得到的估计如何表示不确定性；用户要求应作为硬约束、优化目标还是 Pareto 维度。若这些问题没有明确答案，优化器就可能把不满足实际要求的低成本计划判为可行。

#### 与 P1 的区别

P1 关心“改写属于严格等价、近似还是非法”，P4 关心“允许近似以后，怎样描述、估计和传播质量”。前者确定计划空间边界，后者为候选计划提供质量属性。

#### 与已有工作的边界

Abacus 已支持在成本、延迟和质量约束下选择实现；DocETL 和 MOAR 已评估改写后的任务质量；Cortex AISQL 报告模型级联和 semantic join rewrite 的质量。因此“把质量放入优化目标”本身不是空白。更具体的问题是：质量是否能在混合关系—语义计划中组合、能否在执行前预测最终查询质量，以及近似规则能否提供优化器可检查的质量契约。

### 3.5 P5：AI 算子的物理实现和访问路径缺少统一契约

#### 问题由来

传统逻辑算子通常可以转换为多个结果等价的物理实现。例如，Hash Join 与 Merge Join 的执行方式和物理属性不同，但在相同逻辑条件下应返回相同结果。一个逻辑 `AI_FILTER` 可以由大模型、小模型、级联、embedding 代理或规则程序实现，这些实现不仅成本不同，输出集合也可能不同。对 `AI_JOIN`，优化器还可能没有显式连接键或能够无损排除候选对的访问路径。

物理实现只暴露模型名称和平均延迟时，优化器无法判断它在当前数据、prompt 和查询位置上的实际输出基数、质量、资源需求及适用条件。

#### P5.1：AI 物理实现需要同时描述成本、基数、质量和资源

场景：`AI_FILTER('评论在抱怨噪音', text)` 可以选择本地小模型或远端大模型。

```text
本地小模型：0.05 元/千行，F1=0.82，输出选择率 30%，GPU 并发有限
远端大模型：2 元/千行，F1=0.94，输出选择率 18%，API 并发较高
```

小模型的单行成本更低，却让更多假阳性进入后续 Join 和昂贵算子；大模型自身更贵，但可能减少后续输入。只登记模型价格或平均 F1，无法计算它对整个计划的影响。

物理实现至少需要暴露与当前数据相关的单位或批量成本、输出基数、错误分布、输入长度限制、batch 能力、缓存条件和资源需求。还需确定这些属性是一个点值、分布还是带置信区间的估计。

#### P5.2：Cascade 是包含模型、路由和阈值的参数化物理实现

场景：先用 proxy 判断，置信度不足的记录再交给 oracle。

```text
阈值较宽：大多数记录由 proxy 直接决定，oracle 调用少
阈值较严：更多记录升级到 oracle，成本和质量同时上升
```

阈值改变的不只是该算子的平均调用成本。proxy 的假阳性和假阴性会改变输出选择率，升级样本的输入长度分布可能又不同于全表，最终还会影响下游节点的行数和质量。

因此，Cascade 不能只作为一个具有固定成本的物理算子登记。模型组合、路由概率、阈值、条件错误率和输出选择率共同定义一个参数化物理实现；这些参数形成的候选还会进入 P6 的完整计划空间。

#### P5.3：AI_JOIN 缺少可用于安全缩减候选对的连接结构

普通等值 Join 会向优化器暴露连接键。例如 `q.topic_id = f.topic_id` 明确给出了必要匹配条件，Hash Join、Merge Join 或索引查找可以只生成键值相同的候选对，而且不会因此漏掉结果。下面的 AI_JOIN 只暴露了一个需要模型判断的匹配函数：

```text
M(q.text, f.answer, prompt) -> true / false
```

对 5 万条咨询和 200 条 FAQ，如果没有额外可见结构，优化器无法在调用 `M` 之前证明任意一对一定不匹配。直接执行因而面对 1000 万个候选对。自然语言匹配关系对优化器不透明：没有显式连接键、必要条件或可证明完备的 blocking 规则，系统就缺少能够在保持结果的同时排除候选对的 access path。

这一问题可以继续拆成四项：

1. 哪些自然语言连接条件或数据属性隐含了可供优化器使用的必要匹配条件；
2. 这些条件由用户声明、算子契约、数据分析还是模型推断得到，优化器如何验证其有效性；
3. 无法证明严格完备时，候选生成器应如何描述遗漏概率、recall 下界及其不确定性；
4. prompt、模型、FAQ 集合和数据分布改变后，已经建立的候选缩减条件是否仍然成立。

分类、embedding Top-K、规则 blocking 和“召回后再验证”都是可选物理路线，前置条件并不相同：分类通常要求匹配关系可由相对稳定的标签集合表达；Top-K 检索依赖表示空间能够以足够高的 recall 覆盖真实匹配；规则 blocking 则需要可显式计算的必要或高召回条件。优化器首先要知道每条路线能够排除哪些候选、是否可能漏解，再将适用的物理候选交给 P6 搜索。

#### 与 P6 的区别

P5 关心一个逻辑 AI 算子有哪些可用物理实现、这些实现需要提供什么属性以及是否适用；P6 关心各算子的物理候选与 Join Order、placement、rewrite 和执行参数组合后，如何组织、剪枝和搜索完整计划。

### 3.6 P6：AI 新增计划维度并削弱传统搜索空间组织与剪枝方法

#### 问题由来

传统优化器已经需要搜索 Join Order、访问路径和 Join 算法。AI SQL 又为一个查询增加了多组决策：

```text
T：关系 Join 树和普通算子结构
π：AI 算子的合法 placement 与求值顺序
ι：模型、proxy、cascade、检索器等物理实现
β：batch、并发和请求组织方式
κ：缓存、去重和物化复用策略
ρ：谓词融合、聚合分解、分类或检索后验证等逻辑或近似 rewrite
```

这些维度扩大了候选计划数量，还会相互改变可选项、成本、输出基数和质量。部分 AI 候选计划不再严格等价，传统优化器用于组织等价计划、动态规划复用和基于成本剪枝的方法也需要增加新的计划属性。

#### P6.1：新增决策维度导致候选计划组合膨胀

假设一个包含三个 AI 算子的三表查询，在传统关系部分已有 12 个候选 Join 计划。每个 AI 算子分别有：

```text
3 个合法 placement
4 种物理实现
3 种 batch 配置
2 种缓存策略
```

若暂时把这些选择视为相互独立，仅上述维度产生的候选上界已经是：

```text
12 × 3³ × 4³ × 3³ × 2³
= 4,478,976
```

加入 AI 谓词顺序、cascade 阈值、并发度、谓词融合、AI 聚合分解和 Semantic Join 候选生成后，空间还会继续扩大。阈值和资源参数甚至可能是连续变量，不能直接列成有限候选。

这个计算只是说明新增维度的组合效应。实际计划并不是一个完整笛卡尔积：某些 placement 不合法，某些模型不支持指定上下文长度，而一条逻辑 rewrite 又可能创建或删除整组物理选择。传统 Join 搜索本来就可能指数增长；AI 增加的问题是多个以往不存在的维度会反复附着在每个 AI 算子上，使全量枚举更早失去可行性。

#### P6.2：近似计划难以使用传统等价类和成本支配进行剪枝

Cascades 类优化器把逻辑上等价的表达式放入同一个 Memo Group，再比较其中不同物理实现的成本。例如 Hash Join 和 Merge Join 返回相同结果时，成本更高且物理属性没有优势的计划可以被剪掉。

AI 候选计划可能同时改变成本和结果质量：

| 计划 | 成本 | 最终 Recall |
|---|---:|---:|
| 大模型逐对判断 | 100 | 97% |
| Top-K 召回后验证 | 60 | 93% |
| 小模型分类 | 20 | 80% |

这三个计划不能只按成本互相淘汰。成本为 100 的计划更贵，但可能是唯一满足 `Recall ≥ 95%` 的计划；成本为 20 的计划质量最低，却可能满足只要求 `Recall ≥ 75%` 的查询。它们也不能在不记录质量语义的情况下直接当作传统意义上的等价表达式。

当计划还包含延迟、货币费用、GPU 占用、precision、recall 和置信区间时，支配关系变为多维偏序。质量估计区间互相重叠时，优化器甚至无法确定一个计划是否真的支配另一个计划。近似查询处理过去也需要成本—误差权衡；AI SQL 的新增困难是模型选择、融合、候选缩减和聚合分解等常见计划决策都可能产生不同类型的质量变化，使质量属性广泛进入 Memo 状态和剪枝条件。

#### P6.3：决策相互耦合，分阶段优化可能错过联合最优计划

以 FAQ Semantic Join 为例，不同逻辑选择会产生不同的后续搜索空间：

```text
保留逐对判断：可选择大模型、小模型、batch 和 cache
改写为分类：Cross Join 消失，增加标签模型和多标签阈值
改写为检索后验证：增加向量索引、Top-K 和 verifier
```

逻辑 rewrite 一旦确定，后续物理实现和成本结构随之改变。反过来，如果没有合适的 embedding 索引或 verifier，对应的候选生成路线也没有执行价值。placement 还可能改变输入基数、重复输入比例和 batch 机会，因此各维度不能始终独立优化。

即使只考虑谓词顺序和模型选择，分阶段决策也可能失效。设 100 万行输入上有两个 AI 谓词：

```text
A-oracle：单行成本 2，输出选择率 1%
A-proxy：单行成本 1.5，因假阳性较多，输出选择率 80%
B：单行成本 3，输出选择率 10%
```

若 A 使用 oracle：

```text
A → B：100 万 × 2 + 1 万 × 3 = 203 万成本单位
B → A：100 万 × 3 + 10 万 × 2 = 320 万成本单位
```

A 应先执行。但将 A 独立替换为 proxy 后：

```text
A → B：100 万 × 1.5 + 80 万 × 3 = 390 万
B → A：100 万 × 3 + 10 万 × 1.5 = 315 万
```

最优顺序发生了逆转。先按 oracle 的属性确定顺序、再独立选择更便宜的 proxy，会保留错误的 `A→B` 顺序。在 Join 查询中，模型实现还可能改变 Join 输入基数，Join Order 又会改变重复输入和前缀聚集程度，进一步影响 batch、缓存和模型调用成本。

全量联合搜索可能因 P6.1 的空间规模而不可行，完全分阶段又可能错过联合最优计划。搜索器需要识别真正相互影响的少量决策，在这些局部维度上联合枚举，并对其余维度使用安全的阶段划分或界限剪枝。

#### P6.4：搜索和评价候选计划本身会消耗 AI 预算

传统优化器可以低成本调用解析式成本模型比较大量计划。AI 计划的成本和质量常需要在样本上试跑；若一个 pipeline 有 20 个 rewrite 候选、每个候选再试 3 个模型和 4 个阈值，就有 240 个组合。每个组合评估 100 条样本，优化阶段已产生 2.4 万次逻辑 AI 求值。这与 P6.1 的枚举规模不同：P6.1 关注候选数量和搜索算法开销，P6.4 关注为候选计划取得成本、基数和质量估计所支付的模型调用。

对一次只处理 500 行的小查询，这种搜索通常难以摊销；对每天重复执行、每次处理千万行的任务，它可能合理。需要研究候选生成、支配剪枝、评估预算和停止条件怎样依赖预期执行收益，而不能只比较最终选出计划的执行成本。

#### 与已有工作的边界

Horrila 研究 plan-level placement；Abacus 全局选择 Semantic Operator 的物理实现；Nirvana 同时包含逻辑和物理优化；MOAR 在整个 pipeline 上搜索多目标 rewrites。现有系统已经分别使用限制搜索维度、候选生成、分阶段优化和多目标选择等方法控制空间。仍需明确的是：AI 计划如何进入 Memo 等价类，质量和不确定性需要增加哪些状态，哪些支配规则仍然安全，以及哪些强耦合维度必须进行有限联合搜索。

### 3.7 P7：静态计划和 AI 派生结果容易因运行时状态变化而失效

#### 问题由来

传统优化器也会遇到统计信息过期和资源竞争，但 AI SQL 增加了新的动态因素：远端模型延迟和限流、模型版本切换、prompt 修改、缓存状态、非确定输出以及数据语义漂移。编译期最优计划可能在执行中变差，昨日物化的 AI 结果也不一定仍可直接使用。

#### P7.1：编译期统计与运行时行为可能快速偏离

场景：优化器预计“商品宣称静音”选择率为 5%，远端模型平均延迟为 100 ms。执行前几个 batch 后观察到：

```text
实际选择率：60%
平均延迟：350 ms
限流重试：12%
```

此时原定的小 Hash Table、后续谓词顺序、并发度和查询预算都可能不再成立。但前几个 batch 也可能只是数据倾斜或短时服务抖动，立即换计划反而增加物化和重新调度成本。

需要明确哪些运行时信号能区分暂时波动与计划假设失效；偏离多大时会改变剩余计划排名；已经付出的 AI 调用和中间结果如何计入是否调整计划的判断。

#### P7.2：AI 结果复用的有效性不只取决于数据版本

假设系统将常用判断物化为：

```text
products.claims_quiet BOOLEAN
```

随后发生三类变化：新增商品行、prompt 从“是否宣称静音”改成“是否明确承诺低于 30dB”、底层模型从版本 M1 升级到 M2。新增行可以增量补算；prompt 改变使旧结果的任务定义不同；模型升级则可能只影响一部分边界样本。

优化器可选直接复用、只补算新增行、抽样验证后继续使用、将旧阳性作为候选再验证或全量重算。要比较这些计划，缓存和派生列必须记录数据、prompt、模型、推理参数、时间及质量估计等血缘，并定义每类变化下的兼容关系。

#### P7.3：非确定输出使缓存、一致性和质量评价发生冲突

场景：同一条评论第一次物化判断为“抱怨噪音”，在线重算却返回“只是客观提到噪音”。如果查询读取旧缓存得到真，绕过缓存得到假，那么相同 SQL 在相同数据快照上会因执行路径不同而返回不同结果。

固定随机种子也未必能覆盖远端模型版本变化和非确定服务实现。需要明确一次查询内是否强制复用首次结果、跨查询缓存提供何种一致性、模型升级时旧值如何标记，以及质量评测使用一次输出、重复执行分布还是稳定共识。否则优化器选择缓存或重算就不仅改变成本，也改变查询语义。

#### 与已有工作的边界

[Sema](https://arxiv.org/abs/2603.11622) 已使用 Adaptive Query Execution 动态重排、融合和 batching；Cortex AISQL 也包含自适应机制。因此“AI 查询需要运行时优化”并不是新的判断。仍需具体分析触发条件、编译期与运行期职责边界、状态反馈能否跨查询复用，以及带模型血缘的物化结果如何参与计划选择。

## 4. 七类问题之间的关系

这些问题可以按一个计划从产生到执行的过程串起来：

```text
P1：哪些规则仍然适用，哪些变换严格等价、仅在特定条件下等价或只能近似执行？
          ↓ 决定候选计划边界
P2：每个候选节点会输出多少行？
P3：执行这些节点需要多少时间、token、费用和资源？
P4：候选计划会产生怎样的最终结果质量？
          ↓ 提供计划属性
P5：同一逻辑算子有哪些可用、可比较的物理实现？
P6：怎样组织、剪枝并搜索包含相互耦合决策的完整计划？
          ↓ 形成可执行计划
P7：运行时状态变化后，计划和复用结果是否仍然有效？
```

同一个现象可能同时暴露多个原始问题。例如，商品谓词放在 Join 上方还是下方：

- 为提前执行而拆分语义判断或裁剪上下文是否仍等价，属于 P1；
- 移动后输出多少行，属于 P2；
- 重复输入和缓存怎样影响成本，属于 P3；
- 如果移动时删除上下文，质量变化属于 P4；
- 不同模型实现需要提供什么属性，属于 P5；
- placement 与模型、Join 实现是否需要一起决定，属于 P6；
- 实际选择率或缓存状态变化后是否换计划，属于 P7。

这种交叉不表示分类重复，而是说明优化器需要多个环节共同完成一次计划决策。

## 5. 优先验证的子问题

下面四个子问题范围较小，可以通过可控实验直接验证。

### Q1：AI 基数不确定性何时会导致混合 Join 计划选择失稳

来源：P2，并与 P3、P6、P7 相交。

需要回答：

1. AI 谓词选择率变化时，最优 placement、谓词顺序或局部 Join Order 是否改变；
2. 估计误差多大时会跨过候选计划的成本交点；
3. 误差造成的 plan regret 在常见扇出、倾斜和相关性下是否仍显著；
4. 获取统计信息的成本是否可能高于改进计划带来的收益；
5. 编译期无法区分计划时，执行中的真实基数何时足以改变剩余计划。

可比较的处理路线包括固定默认值、随机采样、学习式估计、鲁棒计划和运行时重优化。

### Q2：AI 物理实现的属性变化何时使分阶段优化失效

来源：P5、P6，并与 P2—P4 相交。

需要回答：

1. proxy、oracle 或 cascade 是否具有不同的有效选择率和错误分布；
2. 实现改变后，原先最优的 placement 或谓词顺序是否逆转；
3. 即使优化器已知真实统计，先定 placement 再选实现是否仍产生稳定 plan regret；
4. 差距是普遍存在，还是只出现在人为构造的极端参数下；
5. 质量约束是否会改变阶段边界和计划支配关系。

可比较的处理路线包括顺序分阶段、迭代式逻辑—物理优化、有限联合搜索和带剪枝的动态规划。

### Q3：AI_JOIN 在没有显式连接结构时能否避免全量候选对求值

来源：P5，并与 P2—P4、P6 相交。

需要回答：

1. 对哪些 AI_JOIN 条件，优化器确实无法在模型判断前安全排除任何候选对；
2. 哪些可观察的数据或谓词结构能够提供严格的必要匹配条件；
3. 只能近似缩减候选时，候选 recall 如何限制最终 Join recall；
4. 标签封闭性、语义重叠、真实匹配数和 Top-K 等因素会在什么条件下造成稳定漏解；
5. 数据、prompt 或模型变化后，候选缩减条件及其质量估计是否仍成立。

第一步不是直接改进分类或检索算法，而是用小规模完整逐对结果建立参照，确认候选空间能否被严格缩减，以及不同近似路线在什么条件下开始漏解。之后再比较分类、embedding Top-K、规则 blocking、检索后验证，以及相应的候选完备性或 recall 契约。

### Q4：推理侧状态何时足以改变关系物理计划

来源：P3、P6、P7。

需要回答：

1. Join 输出是否按 prompt 前缀聚集，会带来多大 batch 或 KV-cache 差异；
2. 重复输入比例和缓存命中是否会逆转 placement 或 Join 实现的优劣；
3. 为改善推理吞吐增加 Sort 或 Repartition 是否值得；
4. 上述结论是否跨模型服务和硬件成立；
5. 哪些状态可以在优化期预测，哪些只能运行时观察。

可比较的处理路线包括固定执行参数、推理感知物理属性、联合成本模型和运行时调度。

## 6. 已有研究覆盖到哪里

截至 2026 年 9 月，以下宽泛方向已经有直接相关工作：

| 方向 | 代表工作 | 已覆盖内容 | 仍需继续核实的边界 |
|---|---|---|---|
| 混合计划中的 AI 算子 placement | Horrila；Cortex AISQL | plan-level placement、关系成本与推理成本权衡 | 与 Join Order、统计不确定性、实现变化的耦合程度 |
| Semantic Filter 输出分布 | Larch；Cortex AISQL；Sema | 学习式选择率预测、运行时采样与谓词顺序等 | 统计与模型及 prompt 的绑定、模型输出与真实语义比例的区分、统计获取成本和跨版本复用 |
| 物理实现与模型选择 | Abacus；Nirvana；Cortex AISQL | 模型、级联或实现的成本—质量选择 | 实现属性是否反馈到混合关系计划的基数和 placement |
| 逻辑与 agentic rewrite | DocETL；MOAR；Nirvana；Cortex AISQL | pipeline rewrite、全局多目标搜索、semantic join 分类改写 | 特定改写可检查的前置条件和查询级质量边界 |
| 运行时优化 | Sema；Cortex AISQL | 动态重排、融合、batching 等 | 重优化触发条件、编译期与运行期边界、反馈复用 |
| 推理执行优化 | FlockMTL 等 | batching、模型和 prompt 抽象、数据库内执行 | 推理侧物理属性是否进入全局关系计划选择 |

因此，应避免使用下面这些过宽的研究结论：

- “AI 谓词没有选择率估计方法”；
- “还没有人研究 AI 算子 placement”；
- “现有系统不能选择不同模型”；
- “AI 查询优化还没有考虑质量”；
- “让 LLM 自动改写查询计划是空白”。

更可靠的做法是：先指定原始问题中的一个子问题，构造现有阶段边界、统计假设或质量模型失败的条件，再逐篇核对其搜索变量、输入假设和实验范围。

## 7. 初版 DEMO

### 7.1 DEMO 的目标

第一版 DEMO 不以实现完整优化器为目标，而是回答：

1. Q1—Q4 描述的失败现象是否真实存在；
2. 这些现象是否在非极端参数和真实模型上稳定出现；
3. 现有方法是否已经处理了相同条件；
4. 哪个子问题的影响最大，值得进一步设计新方法。

实验分成两层：

- **已有现象复现**：复现论文已报告的 placement、顺序、级联和 rewrite 的成本—质量变化，用于校验平台与基线，不作为创新点；
- **候选缺口验证**：进入已有工作未覆盖或只部分覆盖的条件，观察是否出现稳定反例和足够大的 plan regret 或质量违约。

### 7.2 执行底座

[Flock](https://github.com/dais-polymtl/flock) 以 DuckDB 扩展形式提供 `llm_filter`、`llm_complete`、`llm_embedding`、`llm_reduce` 和 `llm_rerank` 等能力，可以作为真实 AI 算子执行底座。

第一版不把 DuckDB 或 Flock 当作已经具备全部 AI 决策的研究优化器，而采用：

```text
外部实验控制器
    ├── 生成数据和参数
    ├── 枚举候选逻辑/物理计划
    ├── 提供估计统计或真实统计
    ├── 强制 DuckDB/Flock 执行指定计划
    ├── 收集关系、推理和质量指标
    └── 计算穷举最优与 plan regret

DuckDB + Flock
    ├── 关系算子执行
    ├── AI 算子真实调用
    └── profiling 与模型调用指标
```

这里的“被测优化器”由外部控制器中的计划选择策略提供；DuckDB 负责执行和传统关系计划，Flock 负责 AI 函数调用。这样可以明确回答“使用谁的优化器”：第一阶段使用我们可控的小规模计划枚举器和若干已知基线，而不是假设 Flock 已经能完成所有 AI-aware 决策。

### 7.3 三阶段实验

#### 阶段一：参数化模拟

用可控函数模拟 AI 谓词：

```text
true_selectivity
false_positive_rate / false_negative_rate
cost_per_tuple 或 cost_per_batch
batch_size
cache_hit_condition
latency_distribution
```

目的不是证明真实模型服从这些参数，而是低成本扫描大范围，找到计划排名逆转的边界和反例区域。

#### 阶段二：DuckDB/Flock 真实执行

把阶段一的关键反例替换为真实 `llm_filter`、小模型、大模型或 embedding 实现，验证：

- 参数范围是否现实；
- 计划排名是否仍然逆转；
- 模拟成本与真实 token、延迟和缓存行为的偏差；
- 结果质量变化是否与人工标注一致。

#### 阶段三：候选方法原型

只有某个子问题被稳定复现后，才实现针对性方法。例如：

- Q1 成立，再比较采样、学习估计、鲁棒计划或运行时重优化；
- Q2 成立，再研究 placement 与实现的有限联合搜索；
- Q3 成立，再研究候选完备性或 recall 契约，以及相应的候选生成方法；
- Q4 成立，再研究 prompt 前缀或 batch 作为物理属性。

### 7.4 工作负载与控制变量

#### 工作负载 W1：两表 Join 与 placement

使用第 2.1 节商品—评论查询，控制：

| 参数 | 初始取值 |
|---|---|
| 商品数 | 1 千、1 万、10 万 |
| 平均评论数，即 Join 扇出 | 1、5、10、50 |
| 商品谓词选择率 | 1%、10%、50%、80% |
| 评论谓词选择率 | 1%、10%、50% |
| 重复商品描述比例 | 0%、50%、90% |
| 缓存 | 关闭、开启但低命中、开启且高命中 |
| batch size | 1、16，以及系统允许的更大值 |

#### 工作负载 W2：三表 Join 与相关谓词

使用第 2.2 节查询，控制两个 AI 谓词的边际选择率及其独立、正相关、负相关关系。第一阶段只允许少量明确的左深 Join 顺序，避免一开始枚举所有 Join 树。

#### 工作负载 W3：AI_JOIN 候选空间及其可缩减条件

使用第 2.3 节查询。先在小规模数据上执行完整逐对判断，得到候选对全集和匹配结果；再比较：

1. 逐对 AI 判断；
2. 封闭标签分类；
3. embedding Top-K retrieval + LLM verification。

显式改变 FAQ 是否具有可用的结构化键、标签是否封闭、标签语义重叠程度、每条咨询的真实匹配数和 Top-K。实验需要分别记录候选对缩减比例、候选 recall、最终 Join precision/recall 和总调用成本，并使用人工标注或小规模完整逐对结果作为参照。这样才能区分“候选空间在什么条件下可缩减”这一问题与某个具体分类或检索算法的效果。

#### 工作负载 W4：推理侧物理属性

改变 Join 输出顺序、共同 prompt 前缀长度、batch 和缓存状态，观察关系计划是否会改变请求组织、前缀复用和推理成本。

### 7.5 候选计划与对照策略

第一版只枚举有限维度：

| 决策 | 候选值 |
|---|---|
| AI 谓词 placement | 最早合法位置、Join 后 |
| 同节点谓词顺序 | P1→P2、P2→P1 |
| 局部 Join Order | 两个指定左深顺序 |
| 物理实现 | oracle、proxy 或简单 cascade |
| batch | 关闭、固定批大小 |
| 结果复用 | 不复用、按完整输入键复用 |
| semantic join 实现 | 逐对、分类、retrieval + verification |

对每组数据与算子参数，穷举器计算真实最优计划：

```text
p* = argmin 实际成本(p), 其中 Quality(p) >= τ
```

被测策略根据其可见统计选择：

```text
p_hat = argmin 估计成本(p), 其中估计 Quality(p) >= τ
```

计划损失使用：

```text
plan regret = 实际成本(p_hat) / 实际成本(p*)
```

对照策略至少包括：

1. DuckDB 默认关系计划；
2. AI 谓词固定尽早执行；
3. AI 谓词固定延后执行；
4. 固定默认选择率的成本选择；
5. 使用真实选择率和真实实现属性的成本选择；
6. 顺序分阶段的 placement→implementation 与 implementation→placement；
7. 小规模联合穷举 oracle。

后续加入采样时，再比较固定样本量与面向计划决策的停止策略。它们属于 Q1 的候选方法基线，不属于第一步的问题定义。

### 7.6 如何确认执行了指定计划

DuckDB 可能自行进行谓词下推、CTE 内联和 Join Order 优化。第一版优先用临时表形成明确物化边界，并保存 `EXPLAIN`、`EXPLAIN ANALYZE`。

局部 Join Order 实验可以使用 DuckDB 控制项：

```sql
SET disabled_optimizers = 'join_order,build_side_probe_side';
```

关闭后按 SQL 中的 Join 顺序构造实验计划，结束后恢复：

```sql
SET disabled_optimizers = '';
```

每个计划都要核对实际执行树，不能把 SQL 文本顺序直接当作物理执行顺序。

### 7.7 观测指标

| 类别 | 指标 |
|---|---|
| 计划 | placement、Join Order、模型、batch、缓存、rewrite |
| 基数 | 各节点估计行数、实际行数、选择率及估计区间 |
| 关系执行 | 中间结果大小、关系算子时间、内存 |
| AI 输入 | 输入元组数、distinct input 数、重复率 |
| 模型执行 | 请求数、input/output tokens、推理时间、排队和重试 |
| 总体成本 | 端到端延迟、估算货币成本、优化时间 |
| 结果质量 | precision、recall、F1、Top-K coverage、查询级质量 |
| 优化结果 | plan regret、质量约束违约率、计划排名稳定性 |

Flock 可通过 `flock_get_metrics()` 提供部分模型侧指标，关系侧指标由 DuckDB profiling 获取。缺少的逻辑输入数、distinct input 数和计划配置由实验控制器记录。

### 7.8 验证假设

- **V1（Q1）**：在非极端选择率、Join 扇出和谓词相关性范围内，AI 基数误差能够改变 placement、谓词顺序或局部 Join Order，并产生显著 plan regret；
- **V2（Q2）**：即使已知真实统计，改变 AI 物理实现仍可能逆转最优 placement 或顺序，使固定的分阶段优化明显次优；
- **V3（Q3）**：缺少显式连接结构时，AI_JOIN 无法无损排除大量候选对；近似缩减产生的候选遗漏随标签封闭性、语义重叠、匹配基数和 Top-K 发生稳定变化；
- **V4（Q4）**：重复输入、缓存、batch 和 prompt 前缀组织可以改变不同关系物理计划的总体排名；
- **V5（P7）**：编译期估计与运行时状态的偏差存在明确区域，会使继续执行原计划明显劣于调整剩余计划。

V1—V5 不要求全部成立。实验的价值也包括否定只在极端参数下出现、收益很小或已被现有机制处理的问题。

### 7.9 收敛条件

一个子问题进入算法研究前，至少应满足：

1. 能构造稳定、可重复的反例或边界；
2. 不只依赖人为设置的极端参数；
3. 在真实模型与真实数据子集上仍可观察；
4. 与已有工作的输入假设或决策空间存在明确差异；
5. 影响能够用 plan regret、质量违约或资源浪费量化；
6. 解决问题的优化开销预计低于可获得收益。

若 Q1 最稳定，再研究统计获取与运行时反馈；若 Q2 最稳定，再研究有限联合搜索；若 Q3 能确认候选空间缩减的结构条件或稳定质量边界，再研究候选完备性、recall 契约和候选生成方法；若 Q4 只在特定推理引擎成立，则应明确定位为系统协同优化，而不是宣称通用优化原理。

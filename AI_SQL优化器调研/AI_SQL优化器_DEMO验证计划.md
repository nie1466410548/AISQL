# AI SQL 优化器：DEMO 验证计划（讨论稿）

本文用于持续整理 DEMO 的验证目标、实验设计和讨论结论。这里先验证问题是否真实、影响是否显著，不直接把采样、联合搜索、候选检索等解决方法当成研究问题。

## 1. DEMO 要回答什么

第一阶段不实现完整 AI SQL 优化器，主要回答四件事：

1. 文档中提出的失败现象能否稳定复现；
2. 现象是否出现在非极端参数和真实模型上；
3. 它是否会造成明显的计划成本差距或结果质量变化；
4. 现有方法是否已经覆盖相同条件。

一个问题进入后续算法研究前，至少应满足：

- 能构造可重复的反例或计划排名边界；
- 不只依赖人为设置的极端参数；
- 在真实模型和真实数据子集上仍然存在；
- 能用 plan regret、质量损失或资源浪费量化；
- 与现有工作的假设或搜索范围存在明确差异。

## 2. 哪些内容不需要单独做 DEMO

以下判断可以通过定义、推导或系统接口直接成立，实验只用于量化，不用于证明其存在：

| 判断 | 原因 |
|---|---|
| AI 谓词输出不是数据库中已有的统计列 | 由执行语义直接决定 |
| 模型输出选择率与真实语义比例不同 | 前者包含模型的假阳性和假阴性 |
| Filter、Ranking、Aggregate 使用不同质量指标 | 由算子任务不同直接决定 |
| 新增决策维度会扩大候选计划数量 | 可以根据候选数量直接计算 |
| 只按成本剪枝可能删除高成本、高质量计划 | 可以用多目标反例直接说明 |

真正需要 DEMO 的，是这些事实在什么条件下会改变计划选择，以及影响有多大。

## 3. 实验主题总览

为避免与 P1—P7、Q1—Q4 混淆，本文使用 `E` 表示实验主题。

| 编号 | 实验主题 | 对应问题 | 优先级 |
|---|---|---|---|
| E1 | AI 改写是否稳定改变结果 | P1、P4 | 高 |
| E2 | AI 谓词统计的适用范围与获取成本如何影响计划选择 | P2、P3、P6 | 高 |
| E3 | Placement 与物理实现分阶段优化是否错过联合最优 | P2—P6 | 高 |
| E4 | Semantic Join 分类与候选缩减方案复现 | P5.3、P4 | 可选复现；研究切入点待细化 |
| E5 | 分别验证结果缓存、batch、前缀复用对计划选择的影响 | P3、P6 | 中；三个子实验独立开展 |
| E6 | 查询部分执行后，如何结合反馈和已有 AI 判断调整剩余计划 | P7 | 后续开展，复用 E2/E3 的实验底座 |

P4 的质量问题不单独设计成一个笼统实验，而是作为 E1、E3、E4 的共同观测维度。

## 4. E1：AI 改写是否稳定改变结果

### 4.1 E1-A：多个 AI Filter 独立执行与融合执行

查询目标：找出内容完整并且态度正面的评论。

```text
计划 A：AI_FILTER("内容完整") → AI_FILTER("态度正面")
计划 B：AI_FILTER("内容完整且态度正面")
```

控制变量：

- 模型和推理参数；
- prompt 表述；
- 文本长度和判断难度；
- 条件是否相关；
- 条件执行顺序；
- 重复执行次数。

记录：

- 两条路径的结果集合；
- “独立执行通过、融合后拒绝”及其反向样本；
- 相对人工标注的 precision、recall 和 F1；
- 调用数、token、费用和延迟；
- 同一输入重复执行的一致率。

验证成立的条件：排除模型自身随机波动后，仍能观察到由融合造成的稳定结果差异，并能说明差异与数据或任务条件之间的关系。

### 4.2 E1-B：AI Aggregate 直接执行与分层执行

查询目标：归纳某商品评论中的主要投诉点。

```text
计划 A：全部原始评论 → AI_AGG

计划 B：
分区评论 → AI_AGG_LOCAL
         → AI_AGG_MERGE
```

控制变量：

- 分区数量和分区方式；
- 输入顺序；
- batch size；
- 合并树形状；
- 投诉点的频率、语义相似度和重要程度。

记录：

- 最终投诉点集合及描述；
- 相对人工投诉点集合的覆盖率和遗漏率；
- 不同分区和输入顺序下的结果一致性；
- 成本、token 和延迟。

验证成立的条件：直接聚合与分层聚合产生稳定、可归因的差异，或者分层结果随分区与合并树发生明显变化。

### 4.3 E1-C：自然语言 Predicate Deduction

该实验后置，选定并复现实际的前置条件推导方法后开展。检查从 AI 谓词 E 推导出的普通关系条件 P，是否能减少 AI 调用而不误删记录。比较：

```text
原计划：AI_FILTER(E)
改写计划：关系前置条件 P → AI_FILTER(E)
```

例如，E 为“评论抱怨噪音”，若推导方法生成 P：`text LIKE '%噪音%'`，则“晚上开着像拖拉机，根本睡不着”可能被提前删除。该例仅说明待检查的错误类型，不代表已有方法一定会生成这一条件。

安全前置过滤要求 E ⇒ P。实验分别检查任务语义上的必要性，以及改写是否保留固定 AI 实现原本会接受的记录；两者不能混同。

使用实际方法生成的条件，在独立测试数据上记录：

- 减少的 AI 调用及包含条件推导、检查开销的总成本；
- 原计划接受、但被 P 提前删除的记录；
- 相对人工标签的假阴性及召回率变化；
- 若方法包含条件自检，自检是否发现误删风险。

人工构造的正确条件、错误条件和边界样本仅用于校验漏删检测流程，不作为现有推导方法存在缺陷的证据。有限测试未发现误删，也不能证明 E ⇒ P 对所有输入成立。未选定实际推导方法前，不将该项列入首批执行。

## 5. E2：AI 谓词统计的适用范围与获取成本如何影响计划选择

使用商品—评论两表查询和客户—订单—商品三表查询，比较合法 Placement、谓词顺序及两个指定的左深 Join Order。实验回答三个问题：

1. 同一任务下，哪些模型、prompt 或实现变化会使旧统计不再适用；
2. 统计失配是否足以造成显著的计划成本损失；
3. 为当前实现重新获取统计，在什么条件下值得。

### 5.0 基础实验：选择率如何影响计划选择

先用 mock 谓词验证选择率变化与计划成本的关系，不调用真实模型。选择器使用准确统计，暂不引入估计误差。

最小例子：对 1,000 条记录执行两个 AND 连接的过滤谓词 A、B。两个谓词的单次成本均设为 1 个模拟成本单位，B 的选择率固定为 20%，A 的选择率分别设为 5%、20%、80%。固定逐记录判断，逐算子过滤，不启用缓存或 batch。

```text
计划一：扫描 → Filter A → Filter B
成本：1,000 + 1,000 × A 的选择率

计划二：扫描 → Filter B → Filter A
成本：1,000 + 1,000 × 20% = 1,200
```

两种计划的最终通过集合相同。A 的选择率为 5% 时，计划一成本为 1,050，更便宜；为 20% 时，两者相同；为 80% 时，计划一成本为 1,800，计划二更便宜。这里仅计谓词调用成本，共同的扫描成本省略。

先跑通这个最小例子，再在已有两表、三表候选计划中扫描选择率，记录每个计划的调用次数、中间结果行数和总成本，检查 Placement 或 Join Order 是否出现成本交点。不要求每类计划都发生切换；没有切换时保留结果，不人为制造结论。

该实验是计划枚举与成本累计的基础校验，不作为 AI 特有挑战的证据。后续实验再验证真实 AI 实现变化是否造成统计失配及实际计划损失。

### 5.1 测量输出统计随实现的变化

固定数据和逻辑任务，分别执行大模型、小模型和不同阈值的 cascade，记录逐条判断和输出选择率。prompt 实验使用表达同一任务的不同模板，避免混入任务含义改变。每轮先改变一个因素，再考虑组合变化。

这里测的是模型输出 true 的比例，不是人工标注中的真实语义比例。通过重复执行检查跨配置差异是否超过自身波动，并记录对应的数据、模型版本、prompt、推理参数和级联配置。

### 5.2 测量复用不适用统计造成的计划损失

设 M1 为旧实现，M2 为当前实现。比较：

| 策略 | 计划选择时使用的信息 |
|---|---|
| 默认统计 | 固定选择率默认值 |
| 旧统计 | M1 的实测输出统计 |
| 当前统计参照 | M2 的实测输出统计 |

三种策略最终都使用 M2 执行。固定候选计划、成本模型、质量口径和其他执行配置，只改变计划选择器可见的 AI 输出统计。候选 Placement 和顺序调整须保持谓词输入、实现及求值约定一致。

第一轮用固定的 M2 逐记录判断结果比较计划，隔离重复推理的随机差异；随后对关键计划做真实执行复核。记录所选计划、节点基数及实际成本：

```text
p* = 枚举候选集合内实测成本最低的计划
plan regret = 所选计划的实际成本 / p* 的实际成本
```

当前统计策略仍可能因代价模型误差选不到 p*，不能直接当作最优计划。建立全量统计和最优参照的实验开销单独报告，不假设在线优化器可以免费获取。

### 5.3 测量获取新统计是否值得

对 M2 使用不同规模的简单随机样本估计统计并选择计划，与直接使用默认统计或旧统计比较：

```text
总成本 = 获取统计的成本 + 所选计划的剩余执行成本
```

样本判断满足复用条件时用于正式执行，剩余成本中不再重复计算对应工作；各策略都须完成相同查询。使用多个随机样本重复实验，记录样本量、计划选择稳定性、统计获取成本和净收益，货币成本与延迟分别报告。

通过改变查询规模和样本量，观察获取的信息何时足以选出较好的计划，以及执行收益能否覆盖统计成本。本阶段使用简单随机采样作为基线，后续再根据结果决定是否研究新采样方法。

### 5.4 模拟实验：选择率估错多少会选错计划，损失多大

**验证目标**

固定数据、谓词的实际判断结果和执行成本，只改变优化器拿到的选择率估计，观察估计偏差在什么范围内导致计划选错，以及选错后的成本损失。5.0 使用准确统计、改变实际选择率；本节固定实际选择率、改变估计值，是 5.2 的模拟版本，不需要调用真实模型。

**最小场景**

1,000 条记录需要同时通过谓词 A、B。用预设布尔值代替 AI 返回结果：A 对第 1—100 条返回 true，B 对第 1—500 条返回 true，其余返回 false。因此 A、B 的实际选择率分别为 10%、50%。这只是用于校验流程的人工数据，不代表真实语义分布。

每次判断计 1 个模拟成本单位，关闭缓存和 batch。候选计划只有两个：

```text
计划一：扫描 → Filter A → Filter B
实际成本：1,000 + 100 = 1,100

计划二：扫描 → Filter B → Filter A
实际成本：1,000 + 500 = 1,500
```

两种计划都返回第 1—100 条记录。这里只累计谓词调用成本，省略相同的扫描成本；每次执行按实际访问的记录读取预设答案并计数，不需要模拟等待。

**怎么测**

1. 执行两个候选计划，取得实际成本最低的计划作为参照。本例参照为计划一，成本 1,100。
2. 给外部计划选择器提供估计值，而不是让它读取全量预设答案。选择器按 `1,000 + 1,000 × 第一个谓词的估计选择率` 估算成本，选择较低者；估计成本相同时固定选择计划一。
3. 固定 B 的估计选择率为 50%，将 A 的估计选择率从 0% 扫描到 100%，步长为 5%。除估计值外，其他条件保持不变。
4. 对每个估计值，执行所选计划，记录实际成本，并计算相对候选最优计划的 plan regret。

例如：

| A 的估计选择率 | B 的估计选择率 | 计划一估计成本 | 计划二估计成本 | 所选计划 | 所选计划实际成本 | plan regret |
|---|---|---|---|---|---|---|
| 10% | 50% | 1,100 | 1,500 | 计划一 | 1,100 | 1.00 |
| 40% | 50% | 1,400 | 1,500 | 计划一 | 1,100 | 1.00 |
| 80% | 50% | 1,800 | 1,500 | 计划二 | 1,500 | 1.36 |

本例中，A 被高估并不一定造成计划损失；其估计选择率超过 50% 后才发生错误切换，实际成本增加约 36%。这是预期的校验结果，不是待证明的新现象。

**输出与后续扩展**

输出每组实际选择率、估计选择率、所选计划、实际调用次数、成本和 plan regret，标出计划切换位置。先确认最小例子与手算一致，再复用已有两表、三表候选计划，检查 Placement 和 Join Order 对统计偏差的敏感程度。

后续每轮只增加一个因素，例如改变单次调用成本或 Join 扇出；若改变谓词相关性，通过调整逐记录通过集合的重叠实现，不独立填写互相矛盾的边际与联合选择率。第一轮不同时扫描所有参数。

该模拟用于确定哪些偏差范围值得真实执行复核。真实 AI 配置之间是否存在这样的统计偏差、是否造成相应损失，仍由 5.1、5.2 验证；重新获取统计是否值得，由 5.3 验证。

## 6. E3：分阶段优化是否错过联合最优

E2 固定当前执行实现，研究统计是否适用及获取统计是否值得；E3 允许选择物理实现，并假设候选实现的真实属性已经知道，研究 Placement 与实现选择能否安全分开。

同一个逻辑 AI Filter 提供三种实现：

```text
Oracle 大模型
Proxy 小模型
Proxy→Oracle Cascade
```

每种实现分别测量：

- 单位或批量成本；
- 输出选择率；
- 假阳性和假阴性；
- 资源与并发限制。

比较以下策略：

```text
策略 A：先确定 Placement，再选择物理实现
策略 B：先选择物理实现，再确定 Placement
策略 C：有限联合枚举 Placement × 物理实现
```

需要回答：

1. 改变实现后，最优 Placement 或谓词顺序是否发生逆转；
2. 即使提供真实统计，策略 A 或 B 是否仍有稳定 plan regret；
3. 质量约束是否会改变计划支配关系；
4. 该现象是否只存在于人为构造的极端参数。

E3 成立后，才进入有限联合搜索、迭代式优化或安全阶段划分等方法研究。

## 7. E4：Semantic Join 分类与候选缩减方案复现

P5.3 讨论语义匹配条件缺少优化器可见的连接结构。下面的实验比较分类、检索和 blocking 等已有方案，定位为效果复现，暂不作为独立研究问题的验证。

Cortex AISQL 第 6.3 节已报告分类改写带来的成本与质量变化：平均 F1 从 0.412 提升到 0.596，平均 recall 从 0.761 降到 0.540；EURLEX 的 recall 从 0.833 降到 0.210。已有结果说明改写可能改变 precision 与 recall 的取舍，不能概括为“分类必然降低质量”。[论文第 6.3 节及表 3、4](https://arxiv.org/html/2511.07663v1#S6.SS3)

场景：将买家咨询匹配到标准 FAQ。

在小规模数据上建立覆盖完整候选对的独立人工标注，记录每条咨询的正确 FAQ 集合，包括多匹配和无匹配情况。另执行完整逐对 LLM 判断，作为执行基线：

```text
Questions × FAQ → 对每个候选对执行语义判断
```

逐对 LLM 判断自身可能误判，不能视为正确答案。相对人工标注计算质量；相对逐对执行计算路径间的结果一致性，两者分别报告。

然后比较：

1. 完整逐对判断；
2. 封闭标签分类；
3. embedding Top-K retrieval + LLM verification；
4. 规则 blocking + LLM verification。

控制变量：

- FAQ 是否具有可用结构化键；
- 标签集合是否封闭；
- 标签语义重叠程度；
- 每条咨询的真实匹配数；
- Top-K；
- 模型和 prompt。

记录：

- 候选对缩减比例；
- 相对人工标注的候选 recall（仅适用于显式生成候选的路线）；
- 相对人工标注的最终 Join precision、recall 和 F1；
- 相对完整逐对执行的结果一致性；
- 调用次数、token、成本和延迟；
- 被提前丢弃的正确匹配。

复现记录各方案的加速、漏检及误匹配变化，不把“检索或分类可能漏解”本身作为新结论。有限样本上没有漏检，也不能证明候选缩减严格完备。

研究切入点待细化：优化器选择候选生成路径时，需要哪些可检查的条件才能判断它满足当前查询的匹配覆盖要求，现有实现提供的信息是否足够。需进一步明确具体决策、可见信息和失败场景，再设计相应实验。

## 8. E5：推理侧特征是否改变关系物理计划

E5 分为三个独立实验，每次只改变一种机制。模型、prompt 和其他执行参数保持一致，记录机制本身的收益及其是否足以改变完整计划的排名。最终分别报告货币成本、端到端延迟和资源消耗。

### 8.1 E5-A：结果缓存是否改变 Placement 的成本排序

场景：筛选描述中宣称静音的商品，并关联其评论。AI 谓词只读取商品描述：

```sql
SELECT p.pid, r.rid
FROM products p
JOIN reviews r ON p.pid = r.pid
WHERE AI_FILTER('商品描述宣称静音', p.description);
```

比较同一查询的两种 Placement：

```text
计划 A：商品 → AI_FILTER → 与评论 Join
计划 B：商品与评论 Join → AI_FILTER
```

分别在结果缓存关闭、冷缓存和预先填充的缓存下执行 A、B。每次比较使用相同初始缓存状态；批大小和并发固定，前缀复用关闭或保持相同状态。缓存键包含完整输入、prompt、模型版本和推理配置，并固定查询内求值与复用约定。

Join 后同一描述可能重复出现，但缓存命中后不必再次请求模型。控制商品描述重复率、Join 扇出、商品是否存在匹配评论、缓存容量及初始覆盖率，测量逻辑求值次数、缓存命中、实际模型请求、缓存查找开销和关系中间结果成本。预填充缓存的生成费用单独记录，区分已有缓存与为本次查询建立缓存。

验证缓存是否仅缩小两个计划的差距，还是在某些条件下逆转排名，以及按输入行数估算的成本是否会选错计划。缓存能够减少重复调用本身属于已有机制，不作为新的研究结论。

### 8.2 E5-B：batch 的实际执行收益是否改变谓词顺序选择

场景：在同一评论表上依次执行两个 AI 谓词 A、B，比较 A→B 与 B→A。前置谓词会改变后续输入数量及长度分布，进而影响批次填充和处理效率。

```text
计划 A：Scan → AI_FILTER(A) → AI_FILTER(B)
计划 B：Scan → AI_FILTER(B) → AI_FILTER(A)
```

先固定一条计划，比较不同批大小，取得各算子的批量成本；再对两条计划使用同一批配置，检查计划排名是否与逐行成本模型的预测一致。固定模型、逐条 prompt、最大并发请求数和服务资源，关闭结果缓存，关闭或控制前缀复用。记录批大小之外的实际在途记录数，避免把并发变化混为批处理收益。

本实验中的 batch 指多个独立请求的批量执行，不把多条评论合成一个新 prompt。实施前确认后端实际支持的是客户端批量提交还是服务端推理批处理，并按实际能力标注；不能仅凭 API 请求数减少推断模型计算量减少。

控制输入规模、文本长度分布、谓词输出选择率和批大小，记录有效批大小、尾批、token、吞吐、排队及端到端延迟。检查输出一致性，避免把质量变化造成的少输出误认为纯执行加速。

验证按单行平均成本累加是否足以比较两条计划，以及加入批量成本后是否改变顺序选择。若只提高吞吐、未改变计划排名，则作为执行收益记录。

### 8.3 E5-C：为前缀复用增加排序是否值得

场景：Join 后使用商品标题及描述作为上下文，逐条翻译评论：

```sql
SELECT p.pid, r.rid,
       AI_COMPLETE(
           '请结合商品信息把评论翻译成英文。商品：' || p.title ||
           '；描述：' || p.description || '；评论：' || r.text
       ) AS translation
FROM products p
JOIN reviews r ON p.pid = r.pid;
```

比较两条执行路径，保证每条记录的完整 prompt 不变：

```text
计划 A：Join → 按原输出顺序调用 AI
计划 B：Join → 按商品排序 → 调用 AI
```

固定 Join 实现、batch 和并发，关闭完整结果缓存。使用不同评论使完整输入不同，同时让同一商品的请求共享前缀。控制共同前缀长度、每件商品评论数、原输出的交错程度和前缀缓存容量；两条路径使用相同初始前缀缓存状态。确认排序后的顺序实际传递到请求提交端，必要时使用物化边界和控制器组织请求。

记录前缀缓存命中或缓存 token、推理时间、排序时间、内存及端到端费用和延迟，比较：

```text
计划 A：Join 成本 + 原顺序下的 AI 成本
计划 B：Join 成本 + 排序成本 + 排序后的 AI 成本
```

验证前缀复用收益是否覆盖排序开销。请求相邻并不保证增加命中；若服务能跨请求顺序复用前缀，排序可能没有收益。若无法控制或观测前缀缓存，则只能报告顺序与性能的关系，不能将加速归因于 KV-cache。结论应注明适用的服务和资源条件。

## 9. E6：反馈、结果复用与剩余计划调整

对应 P7.1—P7.3。使用两个 AI 谓词 A、B 的过滤查询，在批次边界暂停，记录哪些行尚未处理、哪些已完成 A、哪些已完成全部判断。从同一个已执行状态比较后续方案：

1. 继续原顺序和实现；
2. 根据反馈调整未处理数据的谓词顺序，复用符合条件的已有判断；
3. 在查询允许的质量约束下切换模型或 cascade，并按需要补算或回补记录。

需要验证：

- 反馈是否代表剩余数据；仅在 A=true 的行上观察到的 B 选择率，不能直接视为 B 在未处理数据上的选择率；
- 复用已有判断能节省多少后续推理，节省是否覆盖补充反馈和切换开销；
- 更换实现后，哪些旧结果仍可使用，是否需要检查已被过滤的阴性记录；
- 已处理部分与新实现产生的结果合并后，整个查询是否仍满足质量约束。

比较成本从暂停点开始计算，包含补充评估、切换、补算和剩余执行；此前费用作为共同已发生成本单独报告。质量按完整查询结果评价，记录假阴性回补、质量违约和反馈偏差。第一版使用可追溯的中间结果，在最终结果交付前调整计划；实现时确定具体模型、暂停比例及上述三类方案的实验配置。

## 10. 公共实验底座

第一版采用外部实验控制器加 DuckDB/Flock：

```text
外部实验控制器
    ├── 生成数据和实验参数
    ├── 枚举候选计划
    ├── 注入估计统计或真实统计
    ├── 强制执行指定计划
    ├── 收集成本、基数和质量指标
    └── 计算穷举最优与 plan regret

DuckDB + Flock
    ├── 执行关系算子
    ├── 执行真实 AI 函数
    └── 输出 profiling 和模型调用指标
```

这里的被测优化器是外部控制器中的计划选择策略。DuckDB 提供关系执行，Flock 提供 AI 算子执行，不假设 Flock 已经实现本文需要验证的全部 AI-aware 优化。

实验分为三个阶段：

1. **参数化模拟**：扫描较大参数空间，寻找计划交点和反例区域；
2. **真实执行复核**：在 DuckDB/Flock 和真实模型上复现关键反例；
3. **候选方法原型**：只有问题稳定成立后，才实现相应解决方法。
